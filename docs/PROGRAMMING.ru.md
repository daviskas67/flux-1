# Программирование ФЛЮКС-1

Этот гайд учит писать программы для ФЛЮКС-1. Подход — аппаратный: машина это
1-битный CPU, единственная память которого — GRID, поэтому любая программа
сводится к перекладыванию отдельных битов, построению логики из ветвлений и
работе с ROM как с прошивкой. Звук — лишь одна из периферий.

[LANGUAGE.ru.md](LANGUAGE.ru.md) — полный справочник инструкций,
[ARCHITECTURE.ru.md](ARCHITECTURE.ru.md) — модель машины. Здесь — *техника*.

## 1. Ментальная модель

```
ROM (64 КБ) ──► CPU ──► GRID (256 бит = 32 байта) ──► экран (16×16)
                  │
                  └──► 3 квадратных канала (звук, опционально)
```

* **Нет байтов для вычислений.** Единственный тип данных — один бит.
* «Регистры» только `ACC` (1 бит) и `PC` (16 бит).
* `SET`/`CLR` пишут бит. `GET` читает бит в `ACC`. `XOR` инвертирует `ACC`
  относительно бита. `PUT` пишет `ACC` в бит.
* **Нет AND, нет OR, нет ADD, нет вычитания.** Всё это строится из `XOR` и
  условных прыжков. В этом вся игра.

Считайте GRID макетной платой: каждая из 256 позиций — узел, который можно
поднять в «1» (`SET`), притянуть к «0» (`CLR`), прочитать (`GET`) или
перевернуть (`XOR`). Программа — это схема соединений в текстовом виде.

## 2. Hello: бегущий огонёк

```asm
START:
    SET  0x00        ; зажечь первый пиксель
    CLR  0x01        ; погасить второй
    JMP  START       ; цикл (в пределах 64-байтного блока)
```

Сборка и запуск:

```
asmflux firmware/loop.asm -o firmware/loop.flux
flux firmware/loop.flux --tps 4
```

`JMP` достаёт только до текущего 64-байтного блока (см. спеку). Когда
программа вырастает за блок — используйте `JMPF`.

## 3. Триггер: один бит состояния, который меняется

Нельзя прочитать и записать одной инструкцией, и нет «инверсии». Стандартный
приём — **вечная единица**:

```asm
SET  0x0F           ; бит, который никто не сбрасывает
GET  0x00           ; ACC = grid[0x00]
XOR  0x0F           ; ACC = grid[0x00] XOR 1  -> инверсия
PUT  0x00           ; grid[0x00] = ACC  (теперь противоположное значение)
```

Каждый проход этого фрагмента бит 0x00 переворачивается. Это поведение
D-триггера — основа любого счётчика ниже.

## 4. Ripple-счётчик (аппаратного уровня)

Ripple-счётчик инкрементирует один бит; если бит переворачивается 1→0, он
«переносит» в следующий бит, как в настоящих двоичных сумматорах.
`firmware/counter.asm` строит 8-битный счётчик из 8 триггеров:

```asm
START:
    SET  0x0F            ; вечная 1
    ; бит 0
    GET  0x00
    XOR  0x0F            ; ACC = bit0 XOR 1
    PUT  0x00
    JZF  C01             ; новый bit0 == 0 -> перенос в bit1
    JMPF START           ; иначе этот такт закончен
C01:
    GET  0x01
    XOR  0x0F
    PUT  0x01
    JZF  C02
    JMPF START
    ; ... и так далее до бита 7
```

Смотрите: `flux firmware/counter.flux --tps 30 --acc`. 8 бит — первая строка
дисплея. Обратите внимание на **асимметричную длину цикла**: проход, который
меняет только бит 0, — 5 инструкций, проход, меняющий все 8, — 37. Это
настоящее аппаратное поведение; учитывайте его при тайминге.

## 5. Арифметика в софте: ripple-carry полный сумматор

У ФЛЮКС-1 нет ADD. `firmware/adder.asm` реализует сложение побитово через
полный сумматор *схемой в программе*. Для каждой стадии:

```
S_i    = A_i XOR B_i XOR C_in
C_out  = majority(A_i, B_i, C_in)
       = (A_i AND B_i) OR (A_i AND C_in) OR (B_i AND C_in)
```

`AND`/`OR` реализуются как **деревья ветвлений** (CPU в роли логических
вентилей):

```asm
    ; C_out = majority(A,B,C)  (регистры A, B, ячейка переноса C)
    GET  A
    JZF  caseA0
    ; A=1 -> C_out = B OR C
    GET  B
    JZF  caseA1B0
    SET  CARRY            ; A=1,B=1 -> 1
    JMPF next
caseA1B0:                 ; A=1,B=0 -> C_out = C (CARRY не трогаем)
    JMPF next
caseA0:                   ; A=0 -> C_out = B AND C
    GET  B
    JZF  caseA0B0
    JMPF next             ; A=0,B=1 -> C_out = C
caseA0B0:                 ; A=0,B=0 -> 0
    CLR  CARRY
next:
    ; S = A XOR B XOR C
    GET  A
    XOR  B
    XOR  CARRY
    PUT  S
```

Сгенерированный `firmware/adder.asm` соединяет четыре такие стадии (A на
0x00..0x03, B на 0x04..0x07, перенос на 0x08, результат S на 0x09..0x0D).
Сгенерируйте любой тест-вектор и проверьте:

```
python tools/gen_adder.py 13 7
asmflux firmware/adder.asm -o firmware/adder.flux
flux firmware/adder.flux --grid-hex --steps 300
grid hex: 7F 40 ...        ; byte0 = A|B, byte1: S = 0b10100 = 20  (13+7)
```

Весь «ALU» — ~50 инструкций деревьев ветвлений. Вот что значит «1-битный
компьютер»: любая полезная операция стоит вам места в программе.

## 6. Перемещение данных и таблицы в ROM

`COPY dst src16` стримит байт ROM в байт GRID (сразу 8 бит — удобно для
строки). Так прошивка заталкивает данные/кадры/константы в машину состояний:

```asm
    COPY 0  FRAME+0     ; байт GRID[0] = ROM[FRAME+0]
    COPY 1  FRAME+1
    ...
FRAME:
    .byte 0x3C, 0x66, 0x0F, ...
```

` .org` размещает большие таблицы вне кода, а арифметика меток индексирует их:

```asm
    COPY 4  SINE+16     ; байт GRID[4] = SINE[16]
```

Для *побитовых* данных подходят `GET`/`PUT` с вычисляемыми адресами; помните,
что `SET`/`CLR`/`GET`/`PUT` адресуют биты 0..255 напрямую.

## 7. Шаблоны управления потоком

### Конечный автомат

Классический идиом ФЛЮКС-1. Бит состояния (или счётчик) живёт в GRID;
программа читает его и прыгает:

```asm
    GET  STATE
    JZF  S0
    JMPF S1
S0:
    ... код состояния 0 ...
    JMPF LOOP
S1:
    ... код состояния 1 ...
LOOP:
    ...
```

Если состояний больше двух — маленький счётчик и дерево диспетчеризации
(тестируйте старший бит первым, потом следующий — бинарный поиск по битам).

### Поведение «подпрограмм»

Нет CALL/RET. Обычные подходы:

1. **Инлайн** маленьких помощников (вставляйте код там, где нужен).
2. Для повторяемого кода — **таблица переходов в ROM**: храните адреса как
   `.word` и выбирайте счётчиком:

```asm
    COPY TEMP TABLE_IDX    ; индекс из GRID, но таблица в ROM...
```

Адреса 16-битные и живут в ROM, поэтому чистая диспетчеризация по таблице
требует `COPY`, но **прыгнуть на вычисляемый адрес нельзя** — `JMPF` берёт
фиксированный операнд. Значит, таблицы адресов кода на лету не прыгаются.
Вместо этого диспетчеризуйте цепочкой `GET`/`JZF`/`JMPF` (бинарное дерево).
Это честный 1-битный путь.

## 8. Отладка

Эмулятор — ваш логический анализатор:

```
flux prog.flux --steps 20 --grid-hex    ; 20 инструкций, дамп байтов GRID
flux prog.flux --steps 20 --acc         ; плюс регистры каналов
flux prog.flux --tps 4                  ; смотреть вживую, 4 такта/сек
```

`--grid-hex` печатает все 32 байта GRID как hex — так проверяется сумматор
выше. `--steps` двигает машину детерминированно и позволяет осмотреть
состояние в нужной точке.

### Соглашение о раскладке

`SET`/`CLR` адресуют биты 0..255, поэтому держите состояние в младших адресах,
а таблицы — в старших адресах ROM:

| область | применение |
|---------|------------|
| GRID 0x00..0x0F | рабочие биты, счётчики, флаги (строка 0 на экране) |
| GRID 0x10..0xFF | данные, массивы, битмапы |
| ROM 0x0000..    | код |
| ROM 0x3000..    | таблицы данных (`.org`) |

## 9. Звук как периферия

Звук — не смысл машины, но он есть и управляется так же, как всё остальное:
записью битов (параметров каналов) через `SETCH`. Три квадратных канала с
частотой/скважностью/громкостью/модуляцией. См. `FREQ`/`DUTY`/`VOL`/`MOD` в
[LANGUAGE.ru.md](LANGUAGE.ru.md). Главное: **тот же цикл, что считает и рисует,
играет и звук** — каналы опрашиваются каждый сэмпл, так что мелодия это просто
побочный эффект главного цикла.

## 10. Упражнения

1. Измените `counter.asm`, чтобы он считал только 0..3 (остановите ripple на
   бите 1).
2. Напишите программу, которая зажигает квадрат 4×4 и сдвигает его на столбец
   вправо каждый проход (COPY + битмап строки в ROM).
3. Расширьте `gen_adder.py` до 8-битных операндов (A на 0x00..0x07 и т.д.).
4. Реализуйте `A AND B` и `A OR B` как подпрограммы-деревья (инлайн) и
   выразите `majority` через них в 3 строки.
5. Соберите 2-стадийный секвенсор (меандр на бите GRID) и направьте его в
   громкость канала через `MOD` — экран будет мигать в такт писку.
